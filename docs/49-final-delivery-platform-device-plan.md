## 2. 为什么反复没有完成：责任与改进

不能仅凭几轮记录断定“agent能力不足”。已证实的原因有三类：

3. **真实外部条件和权限没有落实。** 实际广告MCP凭证已撤销、服务端包体声明异常、ADB无设备、未获本次开发包上传/后台改动的具体授权。这些确实不能靠客户端自决或编造结果解决，但必须给出操作对象、所需动作与责任人，不能停在“缺环境/待用户”。

## 5. USB采样与启动/内存设计

设备连通后，先只读获取型号、系统、Tap版本、当前前台应用与进程列表。Tap包名/小游戏宿主进程必须从设备实际发现，不能猜包名，更不能假定游戏是独立APK。

使用方式（PowerShell，先选择实际设备及宿主PID；下列有占位变量，不能未赋值就执行）：

```powershell
$adbPath = Join-Path $env:LOCALAPPDATA 'CodexDeviceTools/platform-tools/adb.exe'
& $adbPath devices
& $adbPath -s $deviceSerial shell getprop ro.product.model
& $adbPath -s $deviceSerial shell getprop ro.build.version.release
& $adbPath -s $deviceSerial shell ps -A
& $adbPath -s $deviceSerial shell dumpsys meminfo $hostPid
```

Agent在C5前准备一个有界采样会话：每1秒采集实际宿主及相关子进程PID的meminfo，保存时间、阶段、PID角色、PSS/RSS可用项及平台指标。PID变化重新发现；ADB断开立即记录缺测并暂停，不能补造0值。保存采样摘要与必要原始行，不采集整机无关logcat、私人界面或全部存储。

PSS与RSS分别报告，多个进程不能直接累加RSS当独占内存。宿主自身占用、游戏增量、广告原生解码峰值分开观察；不能只看JS heap。ADB每秒采样可能漏掉瞬时峰值，平台报告是必要补充，不能宣称精确捕获所有峰值。

测试轮次：

1. 空宿主/菜单基线→小游戏冷启→菜单可交互→点击开始→杯/HUD/第一颗落料；冷/热各至少5次，报告单次、中位数与最大值，不用5次声称稳定P95。
2. 连玩5分钟、满杯晃杯、两类广告分别播放/关闭，记录关闭后30秒及返回菜单状态。
3. 连续10轮开局/返回和可用广告循环，记录实例/监听/贴图数量的有界诊断与进程曲线。广告无库存不是可以伪造成功的理由，应保留真实可用样本和缺失项。
4. 同此前约400MB失败机型/系统/Tap/采样口径对比；若当前USB手机不是原失败机型，报告只能关闭当前机型，不能替代原平台失败项。
5. 峰值偏高时按实测归因：广告实例→贴图/图片解码重复→动画/Canvas缓存→场景引用→引擎/宿主。逐项修、同场景重测；不要一上来重压全部图片、扩大加载超时或改物理来掩盖卡顿。

禁止清空Tap应用数据或用户游戏存档来制造冷启。需要全新档时采用明确隔离测试存储/测试账号或取得该数据删除的具体确认；先测旧档。必要的force-stop会影响整个Tap宿主会话，应事先告知，不混为删除数据。
