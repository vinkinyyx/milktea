## 2. 玩家体验与保护范围

点击一次「颠杯」，杯身先短促下压再回弹。杯底和中层能看到小料弹起、横向错位并回落。靠近杯口时主要看到上层往杯内横拨，仍能感到料堆移动。合成只来自自然接触，正常满杯计时继续。

- 动作接受前至少有一个真实有效的杯内刚体。空杯或只有杯外落料时提示「杯里还没有小料」，保留次数。
- 保护接受动作时仍在杯内、已经入杯且未进入洒出过程的小料，以及保护期内由这些小料产生的合成子体。接受动作时已在杯外或已进入洒出过程的小料沿用原轨迹和失败判定。
- 以真实杯口和侧壁判定保护范围，杯身的表现位移不参与计算。完全在杯口下方的保护对象不得穿出杯口或侧壁，允许真实后端的已测接触容差。已露头但圆心仍在杯内的小料可维持露头状态，圆心不得越出口或向外逃逸，不得因启用保护而被顶出。
- 保护覆盖预备、脉冲、碰撞反弹和收势。动作之外的落料失误、自然满杯、原有杯外小料洒出均按当前规则处理。杯口保护不会改变复活资格。

HUD 继续由 `shakeControl()` 统一输出，区分「颠杯中…」「稍等片刻」「颠杯 N」「奖励颠杯 N」「看视频 +1 次」和既有不可用提示。教程文案建议「点一下颠杯，低处小料弹起，靠近杯口的小料向内拨动。杯内小料在动作期间受到保护，满杯仍会结算」。广告、结算、错误页、教程及暂停期间沿用现有命令拦截。

## 3. CUP-01 分层冲量

### 3.1 参数和单位

根 `config/design-baseline.json` 为唯一源，工程资源按原脚本同步。玩法规则建议升至 `design-v0.7-guarded-bump-01`，`motion=guarded_bump_v2`。发布前固定参数，同一对外规则版本对应相同动作语义。开发期间改参数使用新的 buildId。以下值只作为第一版。

| 字段或含义 | 调试初值 | 校验与目的 |
|---|---:|---|
| `launch_delay_ticks` | 6 | 接受后第 6 个固定步施力一次 |
| 低处向上速度增量 | 480 DU/s | 先在 460–480 区间实测，质量换算沿用现有适配器 |
| 向上最终速度上限 | 520 DU/s | 同时受杯口净空和全局线速度限制 |
| 停止给向上增量的净空 | 16 DU | 净空不超过此值时以横拨为主 |
| 向上增量系数达到 1 的净空 | 112 DU | 中间区间平滑过渡，实际增量继续受弹道上限约束 |
| 相邻目标横向错位增量 | 低处 120、高处 160 DU/s | 根据净空插值。相邻稳定序号方向相反 |
| 水平向心偏置上限 | 35 DU/s | 向心偏置小于错位量。靠壁侧改为向内 |
| 相对杯的动作水平速度上限 | 320 DU/s | 按当前杯速和刚体速度计算增量余量 |
| 视觉下压与回弹 | 8 / 16 DU | 杯身前后层一同变化。对齐真实杯口，避免画面误判 |
| 最短动作期、冷却 | 39 / 21 tick | 保护未收势时动作期可延长，冷却从保护解除后开始 |
| 收势速度初始阈值 | 向上 ≤ 20 DU/s，垂直速度绝对值 ≤ 55 DU/s | 同时检查边界、护栏接触和相对杯运动。速度阈值单独达标不足以释放 |
| 收势与诊断上限 | 连续稳定 6 tick，96 tick 诊断上限 | 阈值依实测调整。到上限走故障恢复，不带着失控动量撤掉保护 |

参数进入 TS `ConfigLoader` 与 Python 配置校验。校验有限值、整数 tick、单调阈值、单位、最大速度、可组合的物理边界和规则版本。保持 60 Hz 固定步与现有重力。保护接触容差从实际 `CocosPhysicsAdapter` 后端和实测读取，不能为通过测试任意加宽。当前适配器记录的皮肤与线性容差合计约 2.4 DU，只作为核对起点。

### 3.2 目标与计算

1. 使用 `CupGeometry` 的实际杯内轮廓、当前杯偏移、阶段宽度比例、圆半径和杯体相对速度。采用到杯底和左右内壁的有符号距离判断圆形位置，处理倾斜侧壁和端点。现有只按 y 插值宽度加半径的粗筛可作候选，最终资格以几何和当前刚体一致为准。
2. 以 `h = max(0, rimY - (centerY + radius) - margin)` 得到向上净空，以 `gDU = abs(gravity.y) × duPerSpecPhysicsUnit` 转换重力。向上速度软上限为 `min(upSpeedMax, sqrt(2 × gDU × h))`。净空系数取 `clamp((h - 16) / (112 - 16), 0, 1)` 的平滑插值，两个阈值读取配置。上冲增量取配置增量乘净空系数，再限制到当前向上速度剩余空间。靠近杯口不给新的向上推力。预计算的弹道上限用来调手感，碰撞传力由第 4 节的保护处理。
3. 按 entityId 升序固定施力顺序。根据目标的稳定序号交错分配左右推力，用本局已消耗次数交替两侧初始方向。轻量向心偏置叠加后再限幅，避免原来两项相消。贴近杯壁或高速拖杯时，按相对杯的速度与侧壁剩余空间约束横向增量。近壁对象优先朝可用的杯内空间拨动。
4. 只在 `nextTick === activeStartTick + launchDelayTicks` 时施加这次主脉冲。复用 `applyVelocityImpulse` 和 `CoordinateMapper`，将 DU/s 转为 Box2D 单位，按实际质量换算质心冲量。无需消耗落料 RNG。保护过程中由接触解算产生的反弹与主脉冲分别记录。
5. 玩家点击后立即得到按压反馈，领域接受时才扣一次额度。施力前对象已合成时，对当前继承保护的有效子体施力。正常领域拒绝和重复命令不扣次。准备保护几何或首个物理步失败时按完整 checkpoint 回滚。

## 4. CUP-02 杯口物理保护

### 4.1 几何与接触策略

优先复用真实杯壁和底部，在杯口增加跟随 Kinematic 杯体的临时上挡面，必要时增加两端短接合段来封闭角部。上挡面有效内侧按 Box2D 几何皮肤校正到杯口，跟随真实杯 X 位移及速度。碰撞低弹性，使冲量把向外运动变为杯内方向。杯口表现动画可以有位移，保护件位置由真实杯几何决定。

接触过滤只对当前保护成员生效。先用真实 Web Debug 和目标 Cocos 3.8.8 Box2D 后端验证 `PRE_SOLVE`、单步忽略接触和高速连续碰撞能力，再定生产实现。接触回调只过滤或记录接触。启停、重建和刚体注册放在 world 未锁定的固定步边界。若现有后端的接触过滤或高速能力不足，使用经真实后端验证的等价碰撞约束。不能把源码里出现 `bullet` 或 `PRE_SOLVE` 当作运行效果。 [Creator 3.8 2D 接触回调](https://docs.cocos.com/creator/3.8/manual/en/physics-2d/physics-2d-contact-callback.html)

对已露头的杯内对象，避免直接把挡面插入重叠刚体。先做独立真实后端用例，再选安全的单向碰撞处理或按等级分组的上限几何。约束以圆心留在杯内为下限，横拨不许让露头对象从侧边飞出。它落回杯口以下后转为完整封顶保护，退出该分支时保留同一保护成员身份。任何选择都须通过第 8 节露头、混合尺寸、合成子体和拖杯高速场景，不能把露头对象排除后宣称近满杯全部保护。

保护接触独立于正常杯壁和小料接触。它可以影响物理轨迹，但不得进入小料合成配对、重复计分、伪造入杯标志或把杯外落料当成受保护目标。若接触监听原本用 `entityId=null` 识别普通杯壁，给保护 collider 独立标记并核对事件链。

### 4.2 单步边界与故障行为

每个活动固定步记录受保护对象和杯体的步前状态。解算后、合成与提交领域事件前，核对新圆心及扫掠路径相对移动杯口、斜壁和端点的位置。根据真实后端允许的接触容差，区分轻微接触重叠和实际穿越。对可在一步内越界的路径，优先通过真实后端连续碰撞或经验证的速度限制防止穿透。

仍发生实际穿越时，以专用错误码进入现有整步回滚和技术恢复。恢复检查点包含刚体、杯体、保护成员、计数、RNG 和 pendingSpawn。回滚 tick 不产生分数、奖励、洒出或复活事件，也不把越界快照写盘。禁止只清 `spillTicks`、删除越界对象、把动态节点拖回杯内或用 UI 遮住错误。通过标准为正常测试矩阵中零穿透、零因护栏触发的技术回滚。故障注入单独证明回滚路径可恢复。

### 4.3 合成与释放

合成沿用 world 解锁后的原子替换。如果任一父体受保护，符合杯内条件的子体继承保护身份。创建前以子体半径复核可行位置，复用已有墙面投影。无可行位置时保留父体，本 tick 不计分，后续合法接触再合成。禁止先删除父体、增加分数或创建一个已经越界的子体。

预备期和主脉冲之后，直到满足以下条件才释放保护。

- 已过最短动作期。杯内仍在快速向上运动或即将撞到上挡面的小料继续受保护。
- 以圆心、顶缘、当前速度与碰撞结果核对没有待回落的危险轨迹，连续达到稳定步数。每步使用相对杯速度判断接近杯角的对象，近期仍靠护栏反弹时重置稳定计数。已露头对象按露头约束核对，不能要求其顶缘先降到完全封顶线以下才退出。
- 稳定计数器按固定 tick 推进。保护解除后开始冷却，自动落料恢复正常。
- 到诊断上限仍无法安全释放时保留检查点，进入可恢复错误。不得强制卸掉上挡面。高堆叠和满杯的正常用例需通过收势或原规则结算结束，不能频繁落入诊断上限。

## 5. CUP-03 调度、存档与生命周期

| 状态 | 物理与调度 | 玩家反馈 |
|---|---|---|
| 接受前 | 校验有效目标、额度、暂停和冷却 | 按压反馈，拒绝提示原因 |
| 预备至施力前 | 建立保护，保持真实拖杯，保留自动落料 pendingSpawn | 颠杯中… |
| 脉冲与收势 | 单次主脉冲，杯口约束与正常碰撞继续，暂停自动落料释放 | 杯身回弹、小料重排 |
| 安全释放后 | 回到普通杯体，开始冷却。到期的 pendingSpawn 最多释放一个，杯口受阻走原重试 | 稍等片刻 |
| 暂停、后台或退出 | 暂停冻结保护与冷却 tick。销毁时解绑接触监听、清护栏和 CCD 标记 | 恢复后按现有显式继续流程推进 |
| 满杯或合法洒出 | 正常产生结算或复活状态，保护随 world 暂停或拆除 | 原结算/复活语义 |

最少持久化数据是动作开始 tick、当前保护阶段、稳定计数，以及排序去重的成员 ID 和保护类别。需要额外边界值时仅保存由开始状态确定的最小数值。运行节点、Collider 句柄、监听器和临时探针不进入快照。当前快照为 schema 5 且字段严格，若新增持久字段，按 run schema 6 实现并保留 schema 5 兼容读取。沿用 envelope/profile 现有 schema，除非实现证据证明它们也需升级。

1. `SaveValidator` 校验新版本、成员唯一性与引用、tick/phase 自洽、可恢复的物理约束与上限。保留旧规则合法快照的校验路径。
2. 用 `SaveCodec` 按旧格式验证旧槽 checksum 后再做必要的只读转换。启动阶段不回写旧槽。旧规则未完成局沿用现有提示，取消保留旧档，玩家明确开始新规则局且首存成功后才切换。旧纪录、设置及已提交奖励账本保留。
3. 对 `activeStartTick + launchDelay` 前、当步后、收势、冷却分别保存再恢复。恢复按快照重建对应护栏和碰撞过滤，已经执行的主脉冲不补发。页面隐藏、刷新或技术恢复不补算后台时间、不补扣额度、不新增掉落。
4. `SpillReviveCandidate` 的投影、候选哈希、receipt 和提交恢复规则一起检查。原有杯外对象造成洒出时仍可正常进入复活链。成功复活取消未完成的颠杯保护和未施放主脉冲，保留已消耗次数、现有剩余冷却、同 runId、同分与 120 tick 落料缓冲。若复活前仍在保护期，以复活后的逻辑 tick 为冷却起点；已经处于冷却则保持剩余 tick。若候选投影调整，保存时与实际应用时必须得到同一快照语义。旧候选的哈希按其原始规则验证，不混用新规则。
5. 停止、重开、返回菜单、切世界、rollback 和异常重建都验证资源释放。开护栏时启用的临时连续碰撞或监听必须成对还原。没有护栏时普通局的危险计时、落料、自然洒出和复活结果按原场景验证。

## 6. REC-01 新局保存失败可退出和重试

复现方式为在新局首次持久化前对浏览器本地存储写入注入一次异常。现版本显示 `ERROR`，实际可用按钮仍为「下一步」「跳过并开始」。根因是新局预先进入教程状态，失败只切换 screen，教程绘制仍能覆盖错误操作。 [GameRoot 新局保存](../奶茶挤挤/assets/scripts/presentation/GameRoot.ts#L394)

- 在失败边界清理未完成新局的教程、模态暂停、悬挂输入、定时加载 UI 和失败 world。保留当前已确认的旧 bundle/revision 与原始有效槽。错误层优先于教程、Hud、加载层和触控捕获。
- 显示可操作的「重试保存」或对应「返回菜单」「查看诊断」。重试首先核对双槽可读状态和本次尝试身份。已提交并能从 revision、runId 与校验结果识别时，接纳同一已提交新局。明确写入失败时允许重试同一用户意图。提交不确定时先回读，禁止用过期 CAS 盲写，禁止用仅内存局代替保存成功。
- 返回菜单后，仍能按普通流程继续现有可续局，或明确确认开始新局。对已存在的旧规则局，取消确认和首存明确失败均保持原活动局。若写盘后才发生回读错误，以真实读回结果区分已经提交与仍不确定。
- 用真实鼠标或触屏实际点测试两条动作，回读双槽核对有效 runId、revision、分数及教程标记。故障覆盖首次开局无旧档、已有当前规则档、旧规则切换和写入后结果不确定。现有 `LocalSaveRepository.resolveAmbiguousCommit` 优先复用。

## 7. REC-02 渲染和续局重试保留活动局

已复现普通渲染抛错后点「重试准备」，持久化活动局从原 runId 变为新 runId。现有 `showStartupFailure()` 通用重试回调调用 `startNew()`，因此重试渲染等同于发起新局。续局准备失败也必须按原意图恢复。 [GameRoot 错误重试](../奶茶挤挤/assets/scripts/presentation/GameRoot.ts#L574)

| 失败上下文 | 重试目标 | 通过标准 |
|---|---|---|
| 菜单或初始资源渲染 | 重试资源/菜单渲染 | 可用菜单，旧 bundle 保留 |
| 开新局尚未成功提交 | REC-01 的原始开始意图 | 只在首存成功后切换活动局 |
| 新局已提交，HUD 绘制失败 | 恢复刚提交的 run | 同 runId 和 revision 来源，无第二次开局 |
| 继续上局时资源、world 或绘制失败 | 重新加载原持久化活动局 | 同 runId、分数和次数，暂停等待显式继续 |
| 对局中的普通渲染异常 | 暂停并恢复同局画面，或返回保留原档的菜单 | 同局状态可回读，动作保护可重建 |

错误处理通过明确的当前操作上下文选择目标，避免按文案包含某个词推断失败类别。错误进入后暂停时钟、清无效输入，旧异步回调必须受 owner/generation 检查。成功路径只在界面实际恢复时撤掉错误浮层，核查 `render()` 失败后 `hideOverlay()` 被后续代码无条件调用的路径。返回菜单不能隐式 abandon 或提交清档。持久失败时仍有可操作的返回入口及有限诊断输出。

实际点击验证「重试」「返回菜单」「继续上局」。对照故障前后有效持久快照，检查 runId、分数、额度、revision、护栏状态。分别注入一次性和持续渲染错误，证明恢复不会创建新局、反复递归或吞掉错误界面。优先用现有 Debug 体系或隔离浏览器注入，正式包验证无注入开关。
