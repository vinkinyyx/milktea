# 手机晃杯故障、检查点恢复与性能整改

## 1. 用户证据与当前根因边界

截图地址栏为局域网HTTP页面，错误依次为PHYSICS_TICK_ROLLED_BACK和PHYSICS_CHECKPOINT_UNAVAILABLE；用户补充发生在点击晃杯后。HTTP非可信环境通常无Web Locks，当前Repository为保护跨标签写入转临时模式，activeSaveRepository返回null，旧恢复按钮却仍只尝试持久化仓库。这条“点恢复必无存档”路径已由代码确认。

第一条错误只说明某个固定步失败后回滚，可能在施力、接触、合成替换等阶段；粗错误号不能定位。真实Cocos桌面12种子晃杯、8种子快速移杯均未复现，不归因为VPN、手机负载或网络。新错误页可查看底层lastTickFault和buildId；需在反馈手机用新包再次触发，取得真正异常签名，继续定位。

## 2. 本轮已实现免费恢复

- RunEngine失败时保留事务前纯数据快照，取用时clone；原始RNG/spawnRNG/score/实体/晃杯状态均包含，不每帧额外存新深拷贝。
- 恢复优先本页内存检查点，缺失才读可靠仓库；校验runId/封印/结构后重建世界，保持原局并回安全暂停。临时模式没有跨关闭持久化承诺，但本页仍可恢复。
- 仅存在恢复源且该局未用过本次受控恢复时显示“恢复本局”；无源给返回菜单，不反复展示必失败按钮。恢复异常捕获、锁释放、旧存档保护。
- 技术恢复不看广告、不消费未来复活机会。本轮真实故障注入下repository=null已验证同局/分数/双RNG保持；继续90步正常。

未完成：最初手机晃杯异常的根因、重复故障频率、真实Android浏览器/Tap验证。保留P0，不因为恢复按钮能工作就宣称原故障已修。

## 3. 平台失败与本轮首批优化

用户反馈旧v4已上传且平台测试失败：启动太久、部分机型峰值约400MB。报告原始机型/启动秒数/内存分项暂未获得，400MB作为用户提供的实测事实，不能用浏览器JS heap数替代或否定。

已测源码热点：菜单前`Promise.all`加载71图，42.63MiB art单份RGBA；加6效果图集和原尺寸猫咪共57.46MiB，CPU解码、GPU纹理、宿主Image/Canvas和临时缓冲会叠加，此外还有引擎/音频/物理/浏览器进程。因此57MB与400MB不是矛盾，也不能直接计算整个进程优化百分比。

本轮实际：

| 变更 | 实现与限制 |
|---|---|
| 首屏分阶段 | 菜单仅22项art，解码估算4.75MiB；进入游戏才加载余项，最多4并发；继续存档同样补齐game资源 |
| 构建派生 | 背景宽600，杯层高500（另存display_size保证原DU尺寸）、部分小料≤256、Logo宽600；原稿/根catalog保持 |
| 特效派生 | 图集每格96，6图集约2.81MiB；猫咪高256；播放裁切从实际图宽/4计算，未丢帧 |
| 严格来源核验 | 原稿SHA->变换记录->派生catalog->ZIP，验证71+7；旧原稿验证器不放宽 |
| ZIP | 4,381,190->3,008,364bytes，减少约31%；只是包大小，不是内存降幅 |

本地DPR3对照：旧菜单71图/42.63MiB，新菜单22图/4.75MiB；新游戏69图/约18.51MiB（2项未用延展图不加载）。6图集及猫咪按需另计。杯层节点宽高仍750×1000，美术与碰撞校准保持；首局教程按钮实际可见。对照脚本加入等待以消除测试装置场景竞态，因此`sampleAtMs`不是启动成绩，不用于宣称启动快了几秒。

旧`view.enableRetina(false)`在当前3.8.8标记deprecated。虽然flag为false，高DPR实测画布仍780×1688，**本轮不计任何Framebuffer节省**。后续应查当前引擎/平台真实支持的渲染分辨率策略并核验drawingBuffer、触摸映射和清晰度，不访问私有字段冒充生效。

## 4. 后续性能计划

1. **冷启动分段**：下载/解压/引擎与WASM初始化/配置/菜单首帧/按钮可交互/首局物理就绪，记录同SHA。按[Tap启动优化](https://developer.taptap.cn/minigameapidoc/dev/tutorial/performance/launch/launch-guide/)核实`tap.reportScene`最新参数后接入阶段上报，不提前把加载页按钮当实际游戏就绪。
2. **平台内存分项**：同设备冷启、菜单、首次游戏、200体、结算、20次重开、广告展示/关闭、后台回来各采样JS/native/GPU/整体进程峰值；Android按开发调试面板，iOS用真实WebContent进程Instruments，见[官方性能测试](https://developer.taptap.cn/minigameapidoc/dev/tutorial/performance/performance-test/)。
3. **生命周期释放**：修effects挂可销毁UI根、cat重复请求/Frame释放、普通对象Tween和image引用；长期采用稳定节点/池，退出世界后删除body/contact/closure引用。不靠每帧手动GC掩盖泄漏。
4. **压缩纹理**：官方建议ASTC，见[内存指南](https://developer.taptap.cn/minigameapidoc/dev/tutorial/performance/runtime/memory/)。但本项目ArtAssets目前加载ImageAsset再手建Texture2D，不能只勾选ASTC就声称链路成立；需验证引擎导出格式、实际GPU加载路径、alpha/分辨率/旧机兼容和包内是否仍保留双份。采用能力检测回退，不顺带换引擎。
5. **启动内存重叠**：若common资源包下载必需但图像可延迟解码，分别记录下载与解码；别将“放在Bundle”自动等同远程分包。按包内资源占用决策是否进一步分包，不能用空首屏延后初始化绕评测。

## 5. 验收预算与交付

平台本次报告的实际门槛优先；不得把官方“某些场景1GB风险”理解为用户400MB应当合格。建议内部目标：参考低档机进程峰值≤256MiB、稳定重开不持续增长、可交互启动目标≤5秒（固定网络/缓存/设备），均是待测工程目标，不是平台统一强制阈值或本轮已实现数字。

同一候选至少5次冷启/5次热启、低中高档Android（目标覆盖iOS则补），报告p50/p95/max及原始平台数据。新候选未过平台复测前保持BLOCKED。最后别手改ZIP：重建后更新SHA、版本、resolved策略和所有证据；广告仍关，复活功能未实现不能写入版本说明。
