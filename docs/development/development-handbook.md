# 公共模块合同与开发约定

适用全部阶段。玩法真相来自配置和core；UI、音频、平台回调不得直接改分数或对象集合。字段定义以 [types.ts](../../contracts/types.ts) 为准。

## 1. 模块职责与输出

| 模块/目标文件 | 输入 | 唯一职责/输出 | 禁止做的事 |
| --- | --- | --- | --- |
| ConfigRepository | design-baseline.json | 校验并提供不可变Rules | 运行中偷偷改规则 |
| SessionController | 命令、逻辑tick | 状态转移、runId/epoch、唯一终局 | 直接播音/改贴图 |
| DropController | 指针语义命令、RNG | 检查投放间隔/占位、生成一次对象 | 用Math.random决定掉落 |
| PhysicsAdapter | 物体定义/力 | 创建/查询/安全步进/变换，统一坐标 | 修改分数、奖励 |
| ContactRegistry | begin/end接触 | 活跃接触对集合 | 接触回调中销毁刚体 |
| MergeResolver | 活跃接触、实体表 | 排序、锁父对象、生成合成事务 | 由动画回调决定生成 |
| ScoreService | MergeCommitted | eventId去重并累计分数 | 对投放、时间或分享加分 |
| DangerService | 合格物体与tick | 危险/洒出计数、终局原因 | 因贴图抖动触发失败 |
| ShakeController | Shake命令/券确认 | 唯一扣次、48tick力曲线/30tick冷却 | 每帧再施加一次冲量 |
| SaveRepository | 完整步边界快照 | 双槽写入、校验、恢复 | 把损坏当新局静默吞掉 |
| HUD/IngredientView | 只读状态/事件 | 显示和动画 | 反向改刚体半径 |
| Audio/VfxManager | 领域事件、表现RNG | 播放与资源生命周期 | 消耗掉落RNG |
| PlatformAdapter | 用户动作/平台周期 | 能力、存储、录屏/广告调用 | 伪造不支持能力成功 |
| ApiClient | 已登录会话/请求 | 超时、幂等键、重试分类 | 把平台secret写进客户端 |

## 2. ID、数值与时间

- `runId/requestId/eventId`：UUID字符串；P1可用平台安全随机生成，不能用于奖品凭证。实体ID为局内递增整数，续局恢复nextEntityId。
- tick为从0递增的安全整数，逻辑60Hz。0.45秒=27tick，3秒=180tick，0.75秒=45tick，0.8秒=48tick，0.5秒=30tick。
- DU表示设计单位。规格物理单位100DU，Cocos内部比例由P1-A校准，只在PhysicsAdapter转换。
- 在线时间统一UTC ISO8601传输；日额度用服务器 `Asia/Shanghai` 的自然日。不能以客户端日期入账。
- 分数为非负整数；level为1～9；坐标/速度需有限数。拒绝NaN、Infinity、越界数组和未知字段滥用。
- `rulesVersion` 是竞技规则，`saveSchemaVersion` 是存档格式，`appVersion` 是包体；三者不能混成一个版本。

## 3. 输入与一步执行顺序

每tick：去重并消费输入→应用外力→唯一物理step→更新活跃接触→合成事务→计分→危险/越界→终局→快照/表现事件。输入事件携带目标tick，已过期/属于旧runId/旧epoch的事件拒绝。

拖动只改瞄准DU位置；有效松手产生DROP命令，移出区域/触摸取消不投放。按钮事件先由UI消费；第二根手指不参与当前投放。暂停清掉held pointer，恢复不补一次松手。

## 4. 掉落随机算法

选定 `xorshift32_v1_nonzero_seed`。uint32状态不能为0，nextU32：

```ts
let x = state >>> 0;
x ^= x << 13; x ^= x >>> 17; x ^= x << 5;
state = x >>> 0;
return state;
```

浮点 `u=nextU32()/4294967296`，u<0.55取1级，u<0.85取2级，否则3级。初始化依次抽current和next；成功投放才推进一次预告。测试seed=1的前五个整数为270369、67634689、2647435461、307599695、2398689233。音频变体用不同实例。

## 5. 结果、错误与UI映射

统一 `Result<T>={ok:true,data:T}|{ok:false,error:{code,message,retryable,requestId?}}`。预计拒绝不是异常崩溃：

| code | 行为 |
| --- | --- |
| INPUT_BLOCKED / COOLDOWN | 不生成对象、不扣资源；必要时轻提示 |
| NO_BASE_SHAKES / NO_COUPON | 次数不变；P1不出现线上领券入口 |
| STORAGE_CORRUPT | 提供备份恢复/新局选择，保留诊断 |
| UNSUPPORTED_CAPABILITY | 明确不可用，核心游戏可继续 |
| NETWORK_TIMEOUT | 当前结果未知时查询幂等请求，不盲目重做 |
| UNAUTHORIZED | 刷新平台会话一次，失败回登录/本地模式 |
| CONFLICT_REVISION | 回读云端并按规则合并，不覆盖新数据 |
| DAILY_LIMIT / ALREADY_CLAIMED | 回读余额，提示明确，不能再入账 |
| VERIFICATION_PENDING / REJECTED | 本地成果保留，正式榜待验证/不计榜 |
| RULES_VERSION_UNSUPPORTED | 保留档案，显示版本更新，不强行按新规则续跑旧局 |
| PHYSICS_INVARIANT_BROKEN | 暂停保存诊断，当前在线成绩不公示 |

## 6. 异步生命周期

所有异步请求捕获 `{runId,epoch,requestId}`；完成后核对当前拥有者。切局递增epoch；物理、音效、粒子和计时器停止并释放。在线资源事务若已提交，前端关闭不撤销它，恢复时查询请求结果并按命令ID应用一次。

## 7. 存档与版本

完整对象数组按entityId排序；校验内容包括对象、分数、RNG、current/next、nextEntityId、危险计数、shake状态。当前步合成提交完成后才能快照。checksum是损坏检测，不是防作弊。

双槽协议：读取两个槽→验证JSON/schema/版本/checksum→选最高完整revision；写非当前槽→回读验证→更新指针。指针写失败不删除旧槽；重开按新runId，旧回调不能覆盖新档。

云档分开存“长期进度”和“进行中的run checkpoint”。最高纪录取max、解锁取并集、设置按明确最后写入；不能对两个不同run的物体数组合并。券不在云档，由流水账单独管理。

## 8. 分支与验收

未来开发每个任务保持一份清楚变更，需求编号进提交说明。遵循仓库真实配置，不删除失败测试、不伪造平台响应。缺少外部权限时保留接口及测试替身，但交付注明真实接入未完成。

# P0 · 规格冻结与开发准备

## 目标、输入与交付
输入为用户确认的奶茶杯、九级小料、2D立体质感、抖音候选、个人主体和分享奖励上限。交付规格，不交付可玩游戏。先读 [公共契约](common-contracts.md)、[阶段总表](../12-delivery-phases.md)。
产品负责人核对范围；开发者核对可执行性；美术依据逐项资产清单制作。一个人可承担多角色，但不能省略对应核对。

## 任务顺序
1. 读需求 FR-01～30，标注 P1/P2/P3/P4；每个延期项保留原编号、依赖和验收，不从文档删除。
2. 把数值从 config/design-baseline.json 导入，禁止另抄一份手工常量。运行时配置加载器必须检查九级递增、概率和100、阶段ID唯一。
3. 逐一核对 contracts/types.ts、schema.sql、api.openapi.json、examples.json。它们是待实施契约，接口定义不能被误认为已运行的服务。
4. 美术从 assets/image-elements.csv 按 first_phase 领取任务；音乐从 audio-manifest.csv 领取。未获授权的素材不得写“可商用”。
5. 建立未来开发看板：任务至少记录阶段、FR、涉及文件、验收用例、依赖、状态、提交和证据目录。
6. 把外部依赖建为明确任务：编辑器补丁/后端锁定、平台能力和资质验证、服务端可信发布证据、跨端验分可行性、广告奖励规则。当前未解决，不能填“通过”。
7. 本轮文档静态校验通过后将其归档。后续改规则必须更新规则版本、迁移方案和对应测试。

## 建议的开发任务卡格式

## 变更和冲突
配置、正文、类型与清单冲突时不能任意选一个。玩法数值以配置为基线，字段/API以契约为基线，先修正文档冲突再实现。新字段需要兼容旧存档；新增规则版本不混旧榜。美术偏好变动不应改变碰撞半径。
广告奖励、平台资质、可信发布证据的未决项不能靠初级开发者猜测；完成对应技术验证或业务决定后再启用依赖功能，其余阶段可以继续。

# P1-A · 工程、坐标与物理基础

## 进入条件和本阶段边界
已读P0、物理分册和公共契约。只实现工程骨架、杯和 PhysicsLab，不提前接联网奖励。开发者安装 Cocos Creator 3.8 LTS 的具体补丁后，在 evidence/P1-A/版本/environment.json 记录编辑器、构建目标、集成物理后端及配置摘要；提交工程设置和依赖锁文件。

## 文件与职责
| 目标文件 | 要完成的方法/行为 |
| --- | --- |
| client/assets/scripts/bootstrap/AppRoot.ts | 加载配置→验证→创建服务→加载场景；失败停在可重试错误页 |
| core/ConfigLoader.ts | 解析JSON，校验级别/概率/杯宽/有限数值；返回Result |
| core/Clock.ts | 唯一60Hz时钟、pause/resume、tick递增；不读系统时间判危险 |
| physics/CocosPhysicsAdapter.ts | 实现IPhysicsAdapter，统一DU和引擎单位转换 |
| physics/CupGeometry.ts | 计算三条静态边与投放区；不创建顶部封口 |
| debug/PhysicsLab.ts | 切换重力、三圆、堆积、重开、接触记录和步数显示 |
| scenes/Boot.scene / PhysicsLab.scene | 只装配服务与节点，不写计分规则 |

## 场景与坐标
设计面750×1334DU，世界原点左下；UI局部原点可不同，转换集中在 CoordinateMapper。杯底(195,260)到(555,260)，上口(115,1060)到(635,1060)，危险线1000，出生中心1130。CupGeometry接收中心、底/顶宽、底/顶高和宽度倍率，输出左/右/底静态边。边的厚度和端点连接必须经穿透试验确定，画面内缘与碰撞内缘一致。
动态小料使用圆形刚体、中心锚点；美术高光/表情子节点无碰撞。spec中100DU=1物理单位只是本项目物理坐标约定，不等于Cocos内部PTM默认值。适配器负责转换，业务代码只存DU。

## 单位与时间验证
1. 空场景放无阻尼圆，从已知高度静止释放，关闭接触；0.5秒理论位移122.5DU，1秒490DU。离散积分允许约一个固定步位移的误差，记录实际后判断转换是否正确。
2. 比较30fps与60fps渲染下120个物理tick的位置和速度；业务时钟应都恰好120步。不要以渲染帧数作为物理步数。
3. 先确认所选Cocos版本的自动步进与物理后回调。默认优先使用引擎固定步进；若必须手动步进，先禁用自动步进并记录理由。一个项目只选一种拥有者，禁止自动与手动同时驱动。
4. 页面落后台停止推进；回来不得补算后台几十秒，也不能用无限追帧卡死主线程。后台时间不计危险倒计时。
5. 旋转屏幕/安全区变化只变显示缩放，世界坐标和杯体不重建，不改变比分。

## 物理参数与接触边界
从配置读取重力、密度1、摩擦0.25、恢复0.12、阻尼0.05/0.25、线速上限12单位/秒及角速12rad/秒。求解迭代8/8是试验初值，不保证集成后端暴露同名设置。缺失API应记录映射或限制，不能编造调用。
接触回调只登记规范化父ID对，不销毁或创建刚体。物理步后才允许修改世界。begin/end维护持续接触集合；销毁对象时清理所有相关对。Adapter只返回实体ID与几何，不导入UI和排行榜。

## 执行清单
先创建版本化空工程并确认实际启动/构建方法，记录真实命令，不能凭空假设 npm run dev。然后接配置、坐标映射、杯、一个圆、三圆、九种圆、固定步计数，最后加压力和重开工具。
开发依赖不得执行未经检查的上游脚本；本项目技能快照只提供方法参考。

## 失败与验收
- 加载失败展示“配置读取失败，重试”，禁止用空数组假装游戏启动。
- 三圆静置60秒不穿杯；同级不同级都可碰撞；最高级圆能放入最窄杯底。
- 连续20次重建PhysicsLab，实体数/监听数回到初值，没有旧碰撞回调。
- 固定种子、固定120tick在同一环境可复现；若跨环境偏差，记录，禁止先承诺跨端逐帧一致。
交付完整工程、版本记录、单位试验CSV、30/60fps对照和碰撞录屏。真实跑过才标记通过。

# P1-B · 核心玩法与本地存档

## 输入、目标及模块
输入为P1-A通过的Adapter、配置和contracts/types.ts。本阶段完成经典杯九级玩法，不做账号、榜单和真实分享。Game场景节点：AppRoot / World(CupWalls,IngredientRoot,PreviewRoot) / Presentation(FxRoot) / Canvas(SafeArea,HUD,DropInput,ModalRoot)。
| 文件 | 对外职责 |
| --- | --- |
| core/RunEngine.ts | dispatch(command)、advanceOneTick()、snapshot()、restore()；状态的唯一写入者 |
| core/DropController.ts | 校验x、间隔和出生空间，接受一次投放并推进随机队列 |
| core/MergeResolver.ts | 持续接触对→稳定排序→预留父对象→合成事务 |
| core/DangerJudge.ts | 更新资格、越线累计、溢出和失败原因 |
| core/ShakeController.ts | 校验次数/状态/冷却，计算每tick水平加速度 |
| core/ScoreLedger.ts | 消费唯一合成事件ID，累计整数分数与maxLevel |
| persistence/LocalSaveRepository.ts | 双槽/校验/迁移；不含引擎Node引用 |
| scenes/GamePresenter.ts | 将领域事件转换为节点/声音；不反写分数 |

## 状态机和命令
启动完成进PLAYING并显示首投提示；暂停进入PAUSED，恢复回原状态；失败先SETTLING再RESULTS。UI遮罩期间阻止穿透投放。RESULTS只允许重开/返回，不再接收DROP/SHAKE。
每命令含runId、commandId、sequence、tick；本地异步信封额外保存epoch，不增加网络命令字段。旧局异步结果和重复sequence均拒绝；sequence持续递增。重开先递增epoch、退订、销毁世界，再创建新seed和runId，禁止沿用旧事件队列。

## 随机与投放详细算法
使用非零seed的xorshift32，所有移位按无符号32位归一；u=nextU32/2^32，落在[0,.55)/[.55,.85)/[.85,1)分别1/2/3级。初始化先抽current，再抽next；投放成功后current=next、再抽next；无效投放不消耗随机数。化妆粒子/声音不得用这条RNG。
触摸起始若命中UI就由UI消费到底；游戏区域按拖动更新水平位置，松手投放。把屏幕点转换DU；按当前半径和杯口限制x。最小投放间隔27tick。出生区与其他刚体重叠时显示“杯口被挡住”，不创建刚体、不加dropIndex、不消耗随机；允许移动或晃杯解决，不能永久锁输入。防止同时两个touch各创建一个小料。
新实体分配递增ID、bornTick、level和units；预览始终不是刚体。一次有效投放只发一次DropAccepted。

## 每物理tick严格顺序
1. 取本tick有效命令，校验状态/顺序；DROP加入出生队列，SHAKE请求先判额度。
2. 创建已接受出生实体；给晃杯影响的实体施加F=m×a；物理世界只推进一次1/60秒。
3. 取持续接触集合，先为所有实际接触的动态实体标记dangerEligible；静态杯接触secondId=null也触发资格，但不参与合成。然后过滤已销毁、非同级、9级和未进世界实体。
4. 同级候选先按level升序、中心距升序、较小ID、较大ID排序；逐个预留两个父ID，已预留父不可再用。
5. 在安全边界原子提交父消失/子出现；清理旧接触。新增子本tick不参与第二轮预留，下tick按实际接触继续连锁。
6. 根据唯一MergeCommitted计分；更新危险资格、越线/溢出判定，必要时锁定终局。
7. 提交snapshot修订、事件；表现层最后消费。禁止接触回调直接加分或用粒子完成回调控制合成。

## 合成事务与示例
A/B同级l<9，子等级l+1；子units=A.units+B.units。位置、速度取逻辑质量权重平均并限速；角速度作限幅平均。出生位置不得穿墙，若加大圆与杯边重叠，用三条内半平面投影到可行区域；顶部保持开放，不把越线对象强行压回杯中。刚体重叠的解压交由物理求解，禁止全杯传送。
child.dangerEligible = A.dangerEligible OR B.dangerEligible；bornTick取父最早，hasEnteredCup取OR。这样合成不重复获得免判时间。
逻辑units守恒，因半径增长小于sqrt(2)，视觉占用面积释放；物理质量按密度与新面积计算，不声称真实质量守恒。
子2级+10，子3级+30，4/5/6/7/8/9级分别60/100/150/210/280/360。两次1→2再一次2→3共50分。256个1级理论合到一个9级累计9680分。9+9只碰撞，不合成、不额外得分。
事件ID采用命名空间UUID由runId/tick/parentMin/parentMax确定，保持UUID字段合同；ScoreLedger有去重集合或同tick提交账本。重复接触和重复表现播放不得再加分。

## 危险、溢出与结算
普通新投实体满45tick或首次接触后才具备危险资格。对具备资格实体检测中心y+半径>1000；连续有任意合格越线对象就累加全局dangerTicks，无越线清零。计到180tick以CUP_FULL失败，合成先于本判断。切后台/暂停冻结，晃杯不冻结。
hasEnteredCup仅当实体确实进入杯口下方的有效区域后置true；出生在杯外上方不算溢出。已入杯实体从开放杯口离开、位于杯外持续30tick才以SPILLED结束。穿过侧/底是缺陷，记录物理问题，不能包装成正常溢出。
RESULTS保存最终分、最高小料、投放次数、用券数和原因；无限模式没有通关后强制结束，合到麻薯只提示里程碑。破个人纪录算成绩进步；堆满是本局结束，可继续重开。

## 晃杯
本地每局2次基础机会，P1无额外券。48tick内按配置a(t)=3.2 sin²(πt/T) sin(2π·2.5t)计算水平加速度，T=.8秒，所有动态体F=m×a；外观轻摆≤6DU作用杯与小料的共同表现父节点，碰撞世界不动。使用一次在启动时扣，30tick冷却从结束起算，不能同时重复启动；暂停冻结时长。无实体时可拒绝且不扣次。它不保证合成、不改半径、不删除小料。

## 本地存档
双槽A/B每份{schemaVersion,revision,payload,checksum}，checksum对规范化payload做SHA256用于损坏检测，不是防作弊。先写非活动槽并回读核验，再写活动指针；恢复时取可校验且revision最高者。支持写一半、坏JSON、未知版本回退和显式告知，不能静默清档。
游戏暂停、有效投放/合成/晃杯结束时触发防抖保存；结束立即保存。snapshot保存RNG、计数、危险、每体DU位置速度资格、队列、晃杯进度；P1恢复可暂停在原处，准备完成后玩家点继续。恢复不播放历史得分/声音；重建后清空引擎接触缓存再采集。过期的后台回调按epoch丢弃。
图像/引擎Node/平台token不进存档。旧版本无法迁移时保留原字节备份，提供新开一局且保留个人纪录；云档将在P3另设计。

## 实施步骤与验收
先做单投放→同级合成→多对接触排序→计分→最高级→危险→晃杯→结算→重开→双槽保存→恢复。每步可在debug场景直接摆放坐标，不暴露调试入口给正式玩家。
必测：seed1前五随机值/等级；50分和9680理论账本；3同级只有1对合成；4同级最多2对；持续接触后可继续合；9级不合；179tick不败、180败；暂停不增长；新投出生不误判；旧回调不污染新局；损坏一槽可读另一槽。
交付核心源码、可玩Game场景、测试报告、保存样本和操作录屏。不能把理论算分测试通过写成真实物理已验证。


## 契约补充
实体units从配置level派生，不在IngredientState重复存可冲突字段；事件units必须等于派生父units之和。tutorialCompleted为当前版本布尔标记，若将来新增引导版本再迁移schema。SHAKE_PENDING是UI请求锁，持久状态仍为PAUSED并记录恢复目标。

lastDropTick必须入档，初值null表示从未投放，不能读档绕过27tick间隔。settleStartedTick和challenge保存P4最后一投的收尾起点与题目deadline/budget，经典局为null。Adapter只返回PhysicalBodyState，bornTick/资格/溢出计数由RunEngine维护，不用引擎对象覆盖逻辑字段。
ContactRegistry按contactId维护实际接触，避免同一对象接触两条杯边时一条end误清另一条。顶部离杯以已入杯实体完全越过口沿（centerY-radius>1060）且已离开有效杯内区域开始累计；侧底穿透仍是物理错误。溢出与杯满同tick满足时优先SPILLED，终局仍只提交一次。

## 节点分层与布局
世界层由后到前：背景、杯后壁、假液体底色、配料、前壁高光、杯口前缘、杯底标签。杯前壁透明度保证小料轮廓可辨，装饰不能遮危险线。假液面不产生浮力，也不盖住真实接触。
UI在安全区：顶部当前分/纪录与设置；中段投放区/杯；底部下个小料和晃杯。触摸目标至少48×48 CSS等效像素，750设计面通常不小于96DU；不把可见小图标当触摸框。按钮不覆盖有效投放区。
不同长宽比采用750宽基准适配，可变背景延展，杯保持等比，底部操作和顶部系统区域避让。375×812、390×844、平板及窄屏需检查；画面等比缩放不能压扁物理世界。

## 绑定与动效
MergeCommitted产生子外观、180～240ms软弹、合成环和飘分；动画只缩放精灵子节点。落地轻挤压100～160ms并限幅，持续挤压碰撞不反复播放。危险提示逐渐增强而非全屏闪烁；倒计时为实时文本。晃杯外观不超过6DU，弱动态关闭平移，仅保留低幅提示。
分数直接显示核心累计值，飘分是辅助，不以tween结束累加。多事件同帧可合并飘分表现但不能丢账本。进入暂停所有游戏tween用统一控制，UI关闭动画可继续。恢复档禁止补播过去特效。

## 页面状态清单
首页：新玩家/有续局/配置加载失败；设置：音乐、音效、弱动态、操作偏好；暂停：继续/重开确认/返回确认；结算：普通/新纪录/合到麻薯。关闭确认回原局且不扣机会。

## 声音实现
BGM建议84BPM、60～90秒无缝，主菜单和局内可复用。Drop、轻碰、8级合成音高层次、晃杯、危险、结算、纪录、按钮按音频清单映射。
全局最多8并发SFX；碰撞相对速度<.5单位/秒不响、单体120ms节流、全局碰撞≤6次/秒；严重告警优先普通碰撞。变体使用独立cosmetic RNG，不改变出料。
声音首次用户手势后启动；被系统打断/静音时不阻止游戏。音乐和音效分开保存音量，切后台暂停，回来不叠两条BGM。不做“音乐关了下次又自动开”的默认覆盖。

# P1-D · 回归、性能与探索试玩

## 输入与任务分工
已有P1-C测试包、提交版本、配置摘要和全部P1素材。测试者按09分册用例执行；开发者修复问题后验证受影响路径。5～8人试玩用于发现问题，不是统计显著的商业验证。

## 自动与手工验证
纯逻辑测随机向量、合成去重、危险tick、券未接入时固定2次、最高级、事件顺序和双槽损坏恢复。物理实验测三圆、挤压、连续晃杯、开放杯口、长局堆积、30/60渲染。画面实际检查点击、拖动、UI吞触摸、窄屏和系统遮挡。
为每个用例写前置快照、输入序列、期望状态、实际、版本和证据。测试构造器不得进入正式包或允许玩家调分。发现非确定性时记录seed、tick、对象列表和环境，先定位再重试，不靠扩大容差掩盖穿透。

## 性能采样方法
同一设备至少记录冷启动一次、连续三局和10次重开；静置/密堆/合成连锁/晃杯各采样。记录设备型号、系统、包版本、时长、实体数、drawcall、JS/纹理内存、帧时间P50/P95、固定步耗时、主线程峰值、加载字节。
配置budgets.gate=false表示预算尚未形成发布门禁。不得把浏览器桌面帧率作为低端手机结论。优化按证据：先剔除无效监听、池化纯表现对象、限制粒子与碰撞音，再查图集/纹理和刚体。禁止用降低60Hz逻辑频率改变不同玩家难度。

## 试玩脚本
1. 不讲解，观察是否看懂同级合成、下一颗、危险线和晃杯；记录首次需要帮助的位置。
2. 允许自主玩两局，再问：何处不理解、失败原因是否清楚、晃杯有没有可感知作用、是否愿意再来一局、眼睛/声音是否疲劳。
3. 记录每局时长、最高级、得分、失败原因、基础晃杯使用和误触；不采集无必要的姓名手机号。
4. 五款门槛尚未上线；不能以经典杯少量得分样本就宣布500/800等解锁值合理。
5. 若失败过快，先区分物理bug、引导问题与数值问题。调整数值创建新rulesVersion并保留前后对照。

## 缺陷闭环
B0/B1必须修复后回归。B2列明影响、复现、修复阶段；无法复现也保存证据，不直接标“已修”。每次修复至少重测该用例及相邻流程，例如修存档要同时测结束→重开→继续；修接触要测3/4同级和最高级。

## 交付与验收标准
测试包/运行说明、环境表、cases.csv、原始采样、试玩匿名记录、问题清单、修复提交和acceptance.md齐备。正确性用例通过且无未解决B0/B1才可进入P2；未测设备或未完成听感/素材授权如实登记。P1通过代表本地原型通过，不代表平台上架、排名可信或留存已验证。

解锁按前一杯单局最高分，累计总分不能解锁，解锁不扣分；一次解锁永久保留。边界测499/500、799/800等。每款无限重试，记录独立最高分；经典得分不能写进其他款榜。
服务器已验证成绩可永久解锁；本地未验成绩仅可形成迁移标记/本地练习进度，不能直接写在线榜。离线允许玩本地练习，联网成功后不把它包装为服务器开局的权威成绩。

## 身份与run创建
POST /sessions/exchange仅接受平台code+appid，由服务端请求平台合法接口取得稳定身份；同一(platform,appId,subjectId)唯一。token为随机不可猜会话，只保存散列与过期，日志脱敏。
POST /runs鉴权后检查stage是否解锁、rules可用、mode允许，服务器分配seed/runId、基础2次、最多额外5、初始快照。请求重放同一Idempotency-Key返回原run而非两局。客户端提供的playerId不作为访问依据。
所有run/checkpoint/result必须先校验owner；他人的runId返回拒绝，不能因为知道UUID就能读取存档。

## 云存档CAS流程
GET /progress获得revision。PUT携带expectedRevision；数据库事务锁player_progress行，revision不等返回409 REVISION_CONFLICT并带当前revision；相等才写新档和revision+1。客户端409先拉最新，再向用户说明“其他设备已有进度”并选择继续哪一局；不能悄悄以最后时间覆盖。
永久进度合并使用解锁集合并集、各杯已验证最高分max；设置按用户最近明确选择；activeRun不同不拼接对象列表、不合并分数/RNG/剩余晃杯。每run本身checkpoint也用revision，不混两台并发命令。
导入旧本地最高分只能标imported_local，保留给玩家查看/本地练习；可信排名走新run。未知schemaVersion保留原档并提示升级；不能自动清空永久进度。

## 数据/安全与异常
数据库约束、索引和服务校验都需要，不仅前端隐藏按钮。平台token、会话明文不存客户端可读云档。限制body≤5MiB，数值finite，实体数量按合法投放日志推导；不要把任意JSON直接写数据库。
网络超时保留本地待同步，不显示“已云保存”；重试保持同一幂等键。数据库不可用返回503，不回200假成功。默认环境/密钥用.env.example描述名称，不提交真实值。
备份需演练从测试库恢复；迁移失败停止发布，旧库和旧包仍能读取旧schema。

## 开发顺序与验收
先数据库和测试身份→鉴权→创建run→进度读取/CAS→五杯界面→断网和冲突→本地迁移。使用两个设备/会话模拟同账号修改；检查真实DB行和revision，不以toast为证。
交付迁移、API服务、数据库结果样本（匿名）、五杯资源接入、冲突录屏和接口测试。必须覆盖阈值边界、重复请求、伪造身份、越权run、过期token、断网重试及多设备冲突。

# P3-B · 录屏奖励、晃杯券、可信成绩与榜单

## 进入条件与模块
P3-A账号/云档可用，P2已证实真实发布证据可校验；否则奖励开关保持关闭。待证实的跨端物理验分同样是上线榜单前置，不得以规则写得详细代替技术结果。
模块：RewardService.prepare/claim；CouponService.getBalance/consume；RunVerifier.verify；SettlementService.finish；LeaderboardRepository.list；客户端RewardPresenter/CouponPresenter/LeaderboardPresenter/ShareCardRenderer。API/字段见contracts。

## 奖励业务规则
每成功发布一份新的本局真实录屏可领1张券；同一run最多领1次、同一发布内容不得重复领；同账号北京时间一天最多5张，五杯共享。取消、失败、仅点击分享不得领。
券当日24点过期，基础2次优先使用；一局实际额外用券最多5次，即使跨日也最多5。账户有新券不突破本局上限。每日额度按服务器Asia/Shanghai日历算，不信手机时间。
券余额、当天已领次数、过期时间、当前局额外已用分别展示；“已领取5/5”不等于“还剩5”。首次真用券才从标准局切到助力局，领取但未使用不改变榜分类。切助力后不可切回。

## 发布与发券事务
prepare校验run归属和有效，生成不可猜intentId、过期和服务端nonce，绑定player/run/platform。claim带intent及可验证平台证明；先在事务外执行证据校验并验证发布归属/内容/时效，不能持数据库锁等平台网络。
事务内按固定顺序锁reward_intent→reward_daily(player,Beijingday)→run→coupon批次；新daily行先INSERT ON CONFLICT DO NOTHING再SELECT FOR UPDATE。重复intent或唯一发布ID命中时返回原结果。
重新确认intent未消费、run未领、当天count<5；写share_grants唯一run和platformContent、daily+1、coupon_batches+1、coupon_ledger GRANT+1；同事务提交。第六次返回DAILY_LIMIT且无任何部分写入。
幂等键作用域为(player,route,key)，存请求摘要和响应；同键不同payload返回409，不复用旧结果。平台证明验证失败不产生券，也不把intent标领完；可恢复错误允许重试，永久无效明确提示。
两请求同时冲第五张只能一个成功；每天边界以事务决定的server day为准。平台证明不能可信验证时返回VERIFICATION_UNAVAILABLE，并保留普通分享，不偷偷降级为点击即发。

## 用券事务与游戏时序
基础还有时核心本地先用基础，不调用扣券。需要额外时进入SHAKE_PENDING临时冻结核心，发送runId/commandId/sequence/tick；超时重试同commandId，不递增新请求。
服务端锁run→可用批次，检查active、owner、extraUsed<5、命令序列合法、当天余额>0；扣最早到期批次1、写CONSUME-1和唯一consumeEventId、run.extraUsed+1、board=assisted，同事务保存命令。成功后客户端只应用一次ShakeAccepted并恢复；失败恢复原状态且不执行晃杯。
若服务端已扣但客户端断线，重连拉命令日志和checkpoint，补应用同一consumeEventId；不自动退券又补执行。重开后晚回调因epoch不同不应用到新run。真正放弃已扣且已受理的局不退款，避免反复回滚刷券。
后台过期不删除账本；余额以批次剩余且未过期计算。跨日清额度但不重置run.extraUsed。不得把过期整批原始数量再扣一次导致负数。

## 操作日志与验分
客户端上传规范命令序列和checkpoint；服务器初始seed、规则、投放上限、晃杯授权与命令时间为真值。finish仅置PENDING，不能立即上榜。结构验证检查连续sequence、非倒退tick、合法drop与random、事件父子一次消费、units、得分、资格/终局和次数，拒绝NaN/不可能对象/伪造券。
结构检查不能证明玩家没有伪造碰撞。必须做技术试验：同后端无头回放能否在锁定环境重现碰撞与最终账本。若跨环境不确定，选可验证的规则/运行环境或服务器权威物理方案并形成ADR；未经验证不能标VERIFIED或打开公共权威榜。
状态PENDING→VERIFIED/REJECTED/STRUCTURAL_ONLY；结果查询可轮询退避。PENDING显示“成绩核验中”，本地个人纪录可展示为待核验；REJECTED给可理解原因和反馈入口，不泄漏作弊阈值。
分数只来自服务器确认的合成账本，不信请求score；同run结算一次，重复finish返回同结果。验分失败保留可诊断日志，不把失败自动改成通过。

## 排名与胜负
每杯+rulesVersion+boardType独立榜，取player最高已验证单局分；不同宽度、版本和标准/助力绝不混排。排序先score降序，再达到时间升序、playerId稳定分页；对外名次用RANK，1200/1000/1000/800显示1/2/2/4，较早时间只稳定展示，不打破同分并列。
“超过X%”分母为同榜其他有效玩家数，分子为分数严格低于自己人数；没有其他玩家显示“成为首位挑战者”，不除0、不含自己。不拿虚构机器人当真实人排名。
无限经典没有最终赢遍所有人的通关；玩家刷新纪录、合到麻薯、提高名次就是阶段成就。榜单成绩高于对方可称本次领先，同分并列。具体好友胜负在P4同条件模式定义。
分页cursor包含score/time/playerId和榜快照版本；榜变动时提示刷新，不能重复/漏掉页面又称稳定。移除违规分后重建best，不把玩家历史所有合法分一起删除。

## UI与验收
结算卡包含奶茶款、分数、最高料、规则/标准助力标记和真实截图；昵称/头像来自授权平台或默认，不拉无权限通讯录。分享失败可继续重开。排行榜加载/空/失败/核验中/本人未入榜均有独立状态。
验收：第5/6张、重复intent/content/run、两个并发第五张、改手机时间、跨午夜、基础优先、跨日第6次额外、扣券断网恢复、伪造score、同分、空榜、待核验不入榜、越权领奖。检查数据库前后行和券账本，不只看界面。
交付可信证据试验、验分ADR、事务代码/并发测试、榜单SQL、卡片模板和真机录屏。证据或验分未通过时本阶段不算公开发行完成。


## 长局日志上传协议
无限刷分不能把整局全部事件塞入一个有5MiB限制的finish。每满100条命令或15秒活动时间尝试POST /runs/{runId}/logs，单批最多1000命令/2000事件；超过字节限制先分批，绝不截断账本。
第一批firstSequence=0/previousBatchHash=null；后续批接前次lastSequence+1和batchHash。服务器锁run检查连续性、前驱、命令ID和已经受理的扣券命令是否完全一致；同批重复返回原receipt，改变已收内容返回409。
hash用UTF-8规范JSON（对象键排序、无空格、数组有序，排除batchHash本身）做SHA256；不得用不同序列化格式造成假冲突。hash只防传输变更，不证明客户端诚实。
客户端只在receipt落地本地后清除待传副本；断网继续保存本地队列，重连顺序补传。finish仅带最后小尾部和finalSnapshot；验分读取服务器完整批次+尾部，缺序列保持待补传/拒绝，不以最后100条估全局得分。

# P4-A · 每日同题与好友异步挑战

## 输入与条件
依赖服务器可信run/验分/榜单。只做异步分数挑战，不做实时对战。每题指定stage、rulesVersion、非零seed、投放预算120、基础晃杯2、额外券0；重试无限取最好已验证成绩。

## 模块与数据
server/challenges/DailyService.ts负责北京时间日历生成与唯一(day,rules)题；ChallengeService.create/join/result负责邀请；ChallengeSettlementJob封榜。客户端DailyPresenter、FriendChallengePresenter、ChallengeResultPresenter。
daily_challenges保存seed/budget/openAt/closeAt；friend_challenges保存sourceRun、同题配置和expiresAt；challenge_entries保存每人最佳verifiedRun，不存客户端任意分。
API见/v1/daily-challenges/today和/v1/friend-challenges。服务端从题目读取参数，客户端不可自选seed、增加券或改成更宽杯。

## 开局、结束与截止
服务器北京0点生成当日题，closeAt下个0点；只接受截止前的有效操作，网络提交可有明确有限传输宽限但不能允许截止后继续玩，宽限一旦采用须单独配置并在规则版本记录。默认无额外宽限。
第120次投放后禁投，继续物理最多300tick=5秒后结算，危险/溢出可提前结束。第120次投放本身必须截止前受理；最后5秒也不能越过closeAt继续计挑战分。中途退出可恢复，但不得暂停跨截止获额外时间。
同条件seed只决定出料，玩家落点决定结果；不宣称全玩家轨迹相同。额外券按钮隐藏且服务器拒绝，已有券不被扣。

## 好友创建与胜负
只有已验证、同预算标准daily/friend局可直接作为挑战基准；经典无限局分数不能直接和120投题比较。经典分享卡可邀请进入游戏，若要发公平挑战，先玩一次规定条件的题目。
创建者选择有效期的业务默认需在上线前固定并写入配置；初始实施以当日closeAt为上限，不擅自让挑战永久有效。join校验有效期、账号、版本和题参数，重复加入返回原entry。
未完成一方显示待挑战，不称对方输；双方有verified结果时高分领先，同分平局。挑战截止才确定当前最终胜负；可重试阶段标“暂时领先”。创建者自己也可再刷同题最好分，记录发生时间。
分享参数使用短challengeId，服务端解析归属和题配置，不把可篡改score/seed当可信信息。已过期链接显示结果/今日题入口，不自动创建收费或领奖动作。

## 异常与验收
并发结算只更新更高分，较低重试不能覆盖；PENDING不宣布胜利；已封榜成绩依明确截止规则处理。客户端改时间无效。活动局旧规则不可迁移混榜。
必测同seed前120料一致、122次投放拒绝、额外券拒绝、最后5秒/截止边界、重复join、无成绩一方、平分、过期链接、两次并发高低分。交付题服务、调度重跑记录、DB结果、分享真机和胜负状态截图。

# P4-C · 可选激励广告

## 当前决策
用户接受未来考虑广告，但具体奖励、数额和每天上限未定。config/rewarded-ad-policy.json因此enabled=false，rewardKind=unconfigured，amount/dailyLimit=0。本阶段可以完成能力适配与关闭状态；启用验收需要先确定业务规则，不能由开发者擅自用“再送晃杯”补空白。

## 模块与接口
platform/DouyinRewardedAdAdapter.ts实现load/show/dispose；AdPresenter管理用户主动点击与状态；server/ads/AdIntentService prepare/claim。契约/v1/rewarded-ads/prepare和claim；未配置策略返回FEATURE_DISABLED。
策略包含placementId、policyVersion、rewardKind、amount、dailyLimit、affectsRankedRun。当前建议将未来奖励与排名资源分离，具体奖励仍待确认；cosmetic_token只是接口候选类型，不表示已批准货币玩法。

## 客户端流程
IDLE→LOADING→READY→SHOWING→COMPLETED/CANCELLED/FAILED。只有用户明确点带奖励说明的按钮才show；进入广告先暂停/保存，关闭回来保持可恢复状态。广告无库存、失败、拒看都可回原游戏，不制造必须看广告才能重开的路径。
广告SDK完成事件与普通关闭区分；只关闭未完成不领奖。防止load失败无限重试，使用有限退避；切后台晚回调通过intentId/epoch过滤。广告层不直接修改score、coupon或inventory。

## 服务端与幂等
prepare鉴权、placement/策略版本/额度验证，生成intent。claim检查真实可用完成证明，校验玩家/placement/时效/唯一providerEventId；无法可信验证则保持关闭或只做内部非权益实验，不能假定回调已防伪。
同intent重复claim返回同奖励，事务锁日计数与库存，写grant账本后返回。若将来决定奖励为晃杯券，必须同步修改奖励契约并仍遵守每日5和每局额外5，不能旁路已有上限。退款/作废必须有补偿账本，不直接改余额。
广告密钥仅服务端；埋点不发送无必要个人数据。平台限制和SDK版本在实施时重新核对。

## 验收
未配置时所有入口关闭、服务端拒绝；取消/无库存/断网/重复完成/并发claim/过期intent不双发。完成需核对真实库存与账本。交付适配器、关闭开关、已批准策略（若有）、真实广告证据；业务规则未定时状态为“基础设施可交付，启用待定”，不得标商业化已完成。

# P4-D · 微信与Tap小游戏迁移

## 目标和前置
首发稳定后才扩平台。微信应按“小游戏”能力评估，不能把普通小程序当相同运行环境。Tap小游戏与TapTap发行原生APK是不同交付；APK仅在单独立项后执行，不默认为已有计划。

## 实施步骤与文件
1. 建立platform-matrix.md：主体资格、包体/分包限制、引擎导出、登录、生命周期、录屏/分享、奖励证据、榜/好友、存储、广告、审核与费用；逐项引用实施当时官方来源/后台结果，不复制旧数字。
2. platform/WeChatAdapter.ts、TapAdapter.ts实现同一接口，capabilities真实返回；Local/Douyin保留独立，不用平台判断散落core。
3. 每平台appid/subject通过platform_identities映射；跨平台合并账号必须另有可证明绑定，不因昵称相同自动合并。
4. 在新平台实测物理后端/浮点/帧调度。不能复现原规则的成绩时建立独立rulesVersion和榜，不把更容易端混入同榜。
5. 分享证据不支持时隐藏奖励说明，仅提供可用普通分享；不要把抖音券规则的可信证据假设照搬。
6. 美术导出系统区/图标/截图独立变体，运营文字/隐私/审核材料各平台维护。

## 存档与功能降级
永久解锁可在用户完成合法绑定后迁移；活动局仅在规则/物理兼容已证实时迁移，否则保留原端并提示新端新开局。设置、音量、弱动态独立适配。
UNSUPPORTED是正常能力状态，不伪造success；无录屏不影响单机投放；无好友权限使用邀请链接而非读取通讯录。各平台广告单独策略，不默认开启。

## 验收和交付
至少一台目标真机逐项跑核心回归、生命周期、存档、分享取消、奖励证据、审核和真实发布状态。交付平台矩阵、各Adapter、独立构建、版本/规则映射和实际审核结果。未获资格/SDK权限的平台标外部依赖，不写已支持。若选择APK另做安装、签名保管、隐私与商店发行设计，不在本阶段偷偷引入原生重构。
