# P1-D · 回归、性能与探索试玩

## 输入与任务分工
已有P1-C测试包、提交版本、配置摘要和全部P1素材。测试者按09分册用例执行；开发者修复问题后验证受影响路径。5～8人试玩用于发现问题，不是统计显著的商业验证。

## 自动与手工验证
纯逻辑测随机向量、合成去重、危险tick、券未接入时固定2次、最高级、事件顺序和双槽损坏恢复。物理实验测三圆、挤压、连续晃杯、开放杯口、长局堆积、30/60渲染。画面实际检查点击、拖动、UI吞触摸、窄屏和系统遮挡。
为每个用例写前置快照、输入序列、期望状态、实际、版本和证据。测试构造器不得进入正式包或允许玩家调分。发现非确定性时记录seed、tick、对象列表和环境，先定位再重试，不靠扩大容差掩盖穿透。

## 性能采样方法
同一设备至少记录冷启动一次、连续三局和10次重开；静置/密堆/合成连锁/晃杯各采样。记录设备型号、系统、包版本、时长、实体数、drawcall、JS/纹理内存、帧时间P50/P95、固定步耗时、主线程峰值、加载字节。
配置budgets.gate=false表示预算尚未形成发布门禁。不得把浏览器桌面帧率作为低端手机结论。优化按证据：先剔除无效监听、池化纯表现对象、限制粒子与碰撞音，再查图集/纹理和刚体。禁止用降低60Hz逻辑频率改变不同玩家难度。

## 试玩脚本
1. 不讲解，观察是否看懂同级合成、下一颗、危险线和晃杯；记录首次需要帮助的位置。
2. 允许自主玩两局，再问：何处不理解、失败原因是否清楚、晃杯有没有可感知作用、是否愿意再来一局、眼睛/声音是否疲劳。
3. 记录每局时长、最高级、得分、失败原因、基础晃杯使用和误触；不采集无必要的姓名手机号。
4. 五款门槛尚未上线；不能以经典杯少量得分样本就宣布500/800等解锁值合理。
5. 若失败过快，先区分物理bug、引导问题与数值问题。调整数值创建新rulesVersion并保留前后对照。

## 缺陷闭环
B0/B1必须修复后回归。B2列明影响、复现、修复阶段；无法复现也保存证据，不直接标“已修”。每次修复至少重测该用例及相邻流程，例如修存档要同时测结束→重开→继续；修接触要测3/4同级和最高级。

## 交付与验收标准
测试包/运行说明、环境表、cases.csv、原始采样、试玩匿名记录、问题清单、修复提交和acceptance.md齐备。正确性用例通过且无未解决B0/B1才可进入P2；未测设备或未完成听感/素材授权如实登记。P1通过代表本地原型通过，不代表平台上架、排名可信或留存已验证。
