# P4-D · 微信与Tap小游戏迁移

## 目标和前置
首发稳定后才扩平台。微信应按“小游戏”能力评估，不能把普通小程序当相同运行环境。Tap小游戏与TapTap发行原生APK是不同交付；APK仅在单独立项后执行，不默认为已有计划。

## 实施步骤与文件
1. 建立platform-matrix.md：主体资格、包体/分包限制、引擎导出、登录、生命周期、录屏/分享、奖励证据、榜/好友、存储、广告、审核与费用；逐项引用实施当时官方来源/后台结果，不复制旧数字。
2. platform/WeChatAdapter.ts、TapAdapter.ts实现同一接口，capabilities真实返回；Local/Douyin保留独立，不用平台判断散落core。
3. 每平台appid/subject通过platform_identities映射；跨平台合并账号必须另有可证明绑定，不因昵称相同自动合并。
4. 在新平台实测物理后端/浮点/帧调度。不能复现原规则的成绩时建立独立rulesVersion和榜，不把更容易端混入同榜。
5. 分享证据不支持时隐藏奖励说明，仅提供可用普通分享；不要把抖音券规则的可信证据假设照搬。
6. 美术导出系统区/图标/截图独立变体，运营文字/隐私/审核材料各平台维护。

## 存档与功能降级
永久解锁可在用户完成合法绑定后迁移；活动局仅在规则/物理兼容已证实时迁移，否则保留原端并提示新端新开局。设置、音量、弱动态独立适配。
UNSUPPORTED是正常能力状态，不伪造success；无录屏不影响单机投放；无好友权限使用邀请链接而非读取通讯录。各平台广告单独策略，不默认开启。

## 验收和交付
至少一台目标真机逐项跑核心回归、生命周期、存档、分享取消、奖励证据、审核和真实发布状态。交付平台矩阵、各Adapter、独立构建、版本/规则映射和实际审核结果。未获资格/SDK权限的平台标外部依赖，不写已支持。若选择APK另做安装、签名保管、隐私与商店发行设计，不在本阶段偷偷引入原生重构。
