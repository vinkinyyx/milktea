# 项目设计文档 · 奶茶挤挤（milktea）

> 需求/架构/数据/接口/流程/非功能设计快照。权威细节以 `docs/` 分册与 `config/design-baseline.json` 为准；本文件随需求变动同步更新。

## 1. 需求说明

### 1.1 一句话说明
在透明奶茶杯中投放、碰撞并合成小料的竖屏小游戏：选落点 → 松手投放 → 同级小料接触升级 → 空间有限 → 杯满结算；有限晃杯可腾空间。

### 1.2 已确认方向（用户拍板，不重复询问）
| 项 | 内容 |
| --- | --- |
| 核心玩法 | 同等级小料接触升级，空间渐紧，杯满结算 |
| 操作 | 单指左右拖动、松手投放；按钮晃杯 |
| 主题 | 西米/红豆/珍珠/椰果/仙草/布丁/芋泥/麻薯（九级），容器为奶茶杯 |
| 画面 | 立体质感 2D，固定主视角，不做真实三维 |
| 平台/主体 | 抖音小游戏首发；个人主体 |
| 关卡 | 经典款起，前款单局最高分达标永久解锁下一款（共五款） |
| 重玩 | 不限次数、无体力 |
| 分享激励 | 录屏分享成功奖 1 次额外晃杯，每账号每日 ≤5 次 |
| 商业化 | 测试版无广告；未来评估自愿激励广告（奖励未定） |
| 第一版 | 只做经典款可玩闭环，其余登记延期 |

### 1.3 体验支柱
看得懂（落点/同级/危险清晰）、碰得舒服（无穿透/无飞散、反馈明确）、愿意再来（纪录/解锁/连锁动机，分享非前提）。

### 1.4 版本路线（13 阶段，详见 docs/12）
- P0 设计基线（已交付）
- **P1-A 工程与物理基础（完成 + 修复实现已提交；final14 验收证据归档；九级小料美术源与 PNG 导出已落地；Creator 实机验收仍阻塞）**
- P1-B 玩法闭环 / P1-C 视听 / P1-D 试玩回归（本地可玩测试）
- P2 抖音封闭测试；P3-A/B/C 完整首发（五款、云数据、奖励、验分、榜单、发布）；P4-A～D 扩展运营

## 2. 架构设计

### 2.1 一个核心 + 若干适配器
```text
core（不依赖场景节点与 tt）: Session / Score / MergeRules / Rng / RunCommands / Clock
physics:  PhysicsAdapter（坐标、后端、安全物理步）/ ContactRegistry / MergeCommit / CupGeometry
presentation: IngredientView / HUD / VfxPool / AudioManager（订阅逻辑事件，不拥有分数）
persistence: SaveSchema / LocalSave（双槽 A/B）/ Migration
platform:  LocalAdapter（P1）→ DouyinAdapter（P2）；缺失能力明确标记不可用
services:  P3 起 API、奖励、榜单客户端
```

### 2.2 权威与事件
- 标识：runId / entityId / eventId / epoch 全局唯一、可序列化。
- 核心事件：RunStarted、IngredientDropped、MergeCommitted、ShakeConsumed、DangerChanged、RunEnded、SaveCommitted；后续扩展 ShareRewardGranted、CouponConsumed、ScoreVerified、StageUnlocked。
- 事务规则：合成/计分同一次提交；重复回调不重复计分；异步回调核对账号+请求+epoch；定时由明确系统拥有；规则版本聚合半径/概率/杯形/晃杯/计分/后端摘要。

### 2.3 本地存档（P1-B 实现）
- 内容：schemaVersion、rulesVersion、runId、revision、实体快照、分数/最大小料、当前与下一份、随机状态、dropIndex、机会、危险累计、tick、设置、各款纪录。
- 双槽 A/B：写完整 revision+校验 → 回读校验 → 切索引；异常回退上槽。活跃期约 2 秒一次，暂停/后台/结算即存。
- 损坏处理：告知玩家并提供恢复/新局，不静默清空。

### 2.4 服务端边界（P3 才实施）
沿用 TypeScript + 事务数据库（唯一约束：奖励请求、内容去重、结算 ID、用户/关卡/榜类型/规则版本）。客户端 success 不视为服务端证明；无可靠凭据则调整奖励设计并记风险。

## 3. 数据库表（契约草案，contracts/schema.sql 为准）

逻辑对象：Player、Run、BestScore、StageUnlock、RewardClaim、CouponLedger、ShareContent、Challenge。
关键约束：结算幂等（重复提交返回同一结果）、奖励事务发券（第六张不得超发）、榜单按 关卡+榜类型+规则版本 维度。

## 4. 接口（契约草案，contracts/api.openapi.json 为准，共 22 个 API 操作）

| 接口 | 用途 | 关键规则 |
| --- | --- | --- |
| POST /session/exchange | 平台临时凭证换项目会话 | 私钥仅服务端 |
| POST /runs | 下发 runId/规则/种子/资源 | — |
| POST /runs/{id}/finish | 提交操作日志+合成记录并验分 | 幂等 |
| POST /share-rewards/claim | 录屏奖励核验发券 | 新内容+日额度，事务 |
| POST /runs/{id}/shake | 联网助力局消耗券 | 可查询不重复扣 |
| GET /leaderboards | 分页榜单 | 返回数据时间 |

公开榜启用前验证：资源上限、输入合法性、份数当量、合成路径、计分、终局；未证实确定性前不承诺种子精确复现。

## 5. 核心业务流程

1. **单局循环**：开局（RunStarted）→ 拖动选点 → 投放（IngredientDropped）→ 物理沉降/接触 → 合成原子提交（MergeCommitted，计分一次）→ 危险判定（DangerChanged）→ 杯满结算（RunEnded）→ 存档（SaveCommitted）。
2. **晃杯**：基础晃杯有限次；奖励晃杯消耗券（ShakeConsumed / CouponConsumed），助力局与标准局成绩分榜。
3. **解锁**：前款单局最高分达标 → StageUnlocked，达标不消费分数。
4. **录屏奖励**：分享成功证据核验 → 日额度检查 → 事务发券（ShareRewardGranted），每日 ≤5。
5. **暂停/恢复**：定时系统冻结/释放；恢复完整实体快照后才重连表现与接触。

## 6. 非功能设计

- **性能**：固定物理步进，帧率变化不改规则；性能预算为待实测目标值（报告性质，不伪称达标）。
- **正确性硬验收**：QA-01～35 用例（docs/09）；缺陷分级 B0 阻断 / B1 高 / B2 普通 / B3 建议（docs/12 §4）。
- **合规**：P1 本地测试不对公众发布；P2/P3 上线前重新核对平台资质与隐私要求；素材来源与授权台账（THIRD_PARTY_NOTICES.md）。
- **兼容与回退**（P3-C）：版本兼容/回退演练，回退不破坏存档与券。
- **多平台**（P4-D）：微信/TapTap 迁移各立规则版本，不混物理成绩。

## 7. 待验证/风险（docs/11 摘要）

Creator 实机运行与 Box2D 验收（当前阻塞）、存档恢复偏差、平台分享成功证据可核验性、跨设备确定性复现、游戏名可用性。数值/手感/平衡均为待试玩初值。
